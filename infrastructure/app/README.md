# Application Infrastructure

This folder contains the Docker Compose templates used to run the application in:

- `staging`
- `production-blue`
- `production-green`

These files are used by the Jenkins deployment pipelines, not by local development.

## Purpose

- `staging/`
  Used by Pipeline 2 to deploy the application to the staging VM.
- `production-blue/`
  Used by Pipeline 3 to deploy the blue production slot.
- `production-green/`
  Used by Pipeline 3 to deploy the green production slot.

Each environment runs two services:

- `api`
- `ui`

The Docker images are built by Jenkins and pushed to GitHub Container Registry (`ghcr.io`).

## Files

- `staging/docker-compose.yml`
- `staging/.env.example`
- `production-blue/docker-compose.yml`
- `production-blue/.env.example`
- `production-green/docker-compose.yml`
- `production-green/.env.example`

## Environment Variables

The compose files expect the following values through `.env`:

- `API_IMAGE`
- `UI_IMAGE`
- `API_PORT`
- `UI_PORT`
- `APP_BUILD_SHA`
- `VITE_API_URL`
- `DB_HOST`
- `DB_PORT`
- `DB_USER`
- `DB_PASSWORD`
- `DB_NAME`

The staging template also includes:

- `APP_DEPLOY_COLOR=staging`
- `TEST_DB_*`

The production templates are slot-specific:

- blue slot sets `APP_DEPLOY_COLOR=blue` in the compose file
- green slot sets `APP_DEPLOY_COLOR=green` in the compose file

This is used by the frontend footer to display the current deployment color.

## How These Files Are Used

### Pipeline 2

`Jenkinsfile.staging` uses:

- `infrastructure/app/staging/docker-compose.yml`
- generated `.env` values

The pipeline:

1. builds and pushes the application images
2. copies the compose file and generated `.env` to the staging VM
3. runs `docker compose pull`
4. recreates the staging containers
5. runs integration tests against the live staging environment

This pipeline is triggered from `main`.

### Pipeline 3

`Jenkinsfile.production` uses:

- `infrastructure/app/production-blue/docker-compose.yml`
- `infrastructure/app/production-green/docker-compose.yml`
- generated `.env` values

The pipeline:

1. detects the live production slot
2. chooses the idle slot
3. creates a production DB backup
4. deploys the new version to the idle slot
5. runs pre-switch validation tests
6. switches traffic in Nginx
7. monitors the public endpoint after the switch

This pipeline is triggered manually from the `release` branch after the version has already been validated in staging.

## Manual Usage

If you need to deploy manually on a VM:

1. copy the correct `docker-compose.yml`
2. create a real `.env` from `.env.example`
3. run:

```bash
docker compose pull
docker compose up -d
```

## Notes

- Keep only `.env.example` files in Git.
- Real `.env` files should stay on the target VM or be generated by Jenkins.
- Image tags should point to real images in `ghcr.io`, for example:

```txt
ghcr.io/stranskymaria/simplenotes-api:<tag>
ghcr.io/stranskymaria/simplenotes-ui:<tag>
```
